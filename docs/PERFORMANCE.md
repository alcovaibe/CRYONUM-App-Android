# Производительность: результат и воспроизведение

## Действительно измерено

Android-устройства не было: adb не обнаружил устройств, эмулятор не установлен, /dev/kvm нет.
Следовательно, времена старта/кадров, CPU, RAM, GC, энергопотребление и OCR/PDF latency **не измерены**.
Время Gradle в логах — время сборки в контейнере, не пользовательская производительность.
Размеры собранных APK и SHA-256 находятся в audit/logs/artifacts.json. Сравнение размера с
baseline отсутствует: исходная production-сборка не была доступна без конфигурации Firebase.

Подтверждено чтением кода: старый viewer рендерил все страницы PDF в bitmap и держал список.
Новый рендерит только страницы, нужные LazyColumn, с лимитом 2 млн пикселей/4096 по стороне.
Один ARGB_8888 bitmap ограничен приблизительно 8 млн байт пикселей; общий heap включает
несколько страниц, PdfRenderer, UI и ML Kit и этим числом не ограничен. PdfRenderBudget проверен
unit-тестом. Это снижение алгоритмической верхней нагрузки, а не измеренный процент ускорения.

Калькулятор перенесён с UI на Default с лимитами ввода/битов/времени. Хеширование локальных
лекций вынесено на IO. OCR читает ограниченный файл и декодирует уменьшенное изображение
вне главного потока. Для каждого изменения нужны замеры на устройстве.

Сохраняется заданная в SplashActivity задержка 600 мс для заставки; её влияние на полный
startup не измерено. Отдельное решение об удалении заставки в этом аудите не принималось.

## Протокол владельцу

Использовать две отдельные физические модели: около 1 ГБ RAM (предпочтительно API 26,
ARMv7) и 4 ГБ RAM (ARM64, актуальная ОС). Записать manufacturer/model/API/ABI/фактическую RAM,
SHA, вариант сборки, заряд/температуру, refresh rate, состояние сети и свободное место.
Эмулятор с 1 ГБ не заменяет слабый физический аппарат. Не сравнивать debug с release.

1. Собрать release с тестовой подписью локально, без production-ключа в чате. При необходимости
   добавить временную profileable-конфигурацию в отдельной ветке; обычный localAudit debug
   пригоден для функциональных тестов, но не для выводов о скорости.
2. Для холодного старта 10 повторов force-stop и `adb shell am start -W -n
   com.cryonum.audit/com.cryonum.activity.SplashActivity`. Для тёплого старта возврат из фона без
   force-stop. Отделить системное время запуска от готовности контента/политики.
3. Perfetto/Android Studio Profiler: 60 секунд набора калькулятора, длинные цепочки, factorial
   на лимите, ошибка и отмена. Записать frames/jank, main-thread slices, CPU, аллокации и GC.
4. Открыть все 12 PDF, прокрутить/масштабировать 5 минут, затем выйти. Снять
   `adb shell dumpsys meminfo com.cryonum.audit` до/пик/после; проверить отсутствие монотонного роста.
5. OCR фото 12/48 Мп, поворот EXIF, отказ разрешения, отмена и выход из Activity; 10 повторов.
6. Загрузки через локальный стенд: медленные байты, обрыв, Range, смена ETag, отмена/restart,
   две заявки; затем нехватка места и убийство процесса. Измерить traffic и WorkManager progress I/O.
7. История >50 операций, события >2000; проверить лимиты и размер SQLite/файлов после перезапуска.
8. Battery Historian/Perfetto для фоновой работы за сутки без искусственного публичного трафика.

Сохранять сырые traces, медиану и диапазон повторов. В этом аудите эти клетки остаются
«не проверено», а не нулями. Официальные рекомендации: https://developer.android.com/topic/performance/memory
и https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running
(сверены 2026-09-07).
